04 · Hallazgos y Remediaciones Frontend (1/2)

Mitigación de Esquemas Peligrosos (XSS) y Redirección Abierta

FE-SEC-001 · FE-SEC-002
FE-SEC-001 · Enlace Externo Sin Validar Media · CWE-79 / CWE-1022

Ubicación: src/pages/shared/EventDetailPage.tsx:138-144
Hallazgo: event.enlace se inyectaba directamente en <a href={event.enlace} target="_blank" rel="noreferrer">. Si un registro contuviera un esquema javascript: o data:, podría ejecutarse en el contexto del origen; además faltaba noopener explícito. 

// Antes
<a href={event.enlace} target="_blank" rel="noreferrer">

// Después (Remediado)
/^https?:\/\//i.test(event.enlace) ? (
  <a href={event.enlace} target="_blank" rel="noopener noreferrer">
    {event.enlace}
  </a>
) : event.enlace
✓ Verificado con npm run typecheck && npm run build
FE-SEC-002 · Validación de Rutas Internas Baja · CWE-601 (Open Redirect)

Ubicación: LoginPage.tsx:45 · NotificationsPage.tsx:51 · NotificationDrawer.tsx:40
Hallazgo: navigate(state.from) y navigate(item.url) no verificaban que el destino fuera una ruta relativa interna de una sola barra (rechazando URLs relativas de protocolo como //evil.com). 

// LoginPage.tsx (Remediado)
const safeFrom =
  state?.from && state.from.startsWith('/') &&
  !state.from.startsWith('//') && state.from !== '/login'
    ? state.from : '/';
navigate(safeFrom, { replace: true });

// NotificationsPage.tsx & NotificationDrawer.tsx
if (url && url.startsWith('/') && !url.startsWith('//'))
  navigate(url);
✓ Defensa en profundidad contra Open Redirect

FE-SEC-003 · Purga de Caché al Iniciar Sesión Baja · CWE-200

Archivo: src/queries/session.ts:57-62
Aunque useLogout() limpiaba el caché, useLogin() solo invalidaba sessionKeys.me. En un computador compartido (ej. laboratorio universitario) donde expiró la sesión previa sin cerrar sesión manualmente, podían persistir brevemente datos en memoria del usuario anterior. 

onSuccess: async () => {
  queryClient.clear();
  await queryClient.invalidateQueries({ queryKey: sessionKeys.me });
  await queryClient.refetchQueries({ queryKey: sessionKeys.me });
}

08 · Hallazgos y Remediaciones Backend (2/2)

Endurecimiento de Errores, OTP, Logging y Almacenamiento

BE-SEC-002 .. BE-SEC-007
BE-SEC-002 · Correlation ID en Errores 5xx Baja · CWE-778 (§15)

src/middleware/error.ts no generaba identificador de correlación en fallos 500. Ahora genera un UUID, añade la cabecera X-Correlation-Id y registra { err, correlationId } sin filtrar stack traces al cliente. 

const correlationId = randomUUID();
res.setHeader('X-Correlation-Id', correlationId);
logger.error({ err: error, correlationId }, 'Error no controlado');
BE-SEC-003 · Validación Zod de Cooldown OTP Baja · CWE-20

src/utils/otp.ts leía Number(process.env.OTP_RESEND_COOLDOWN_SECONDS) sin validación. Ahora se valida al arranque en src/config/env.ts como entero positivo (default: 60), impidiendo desactivar el cooldown con valores inválidos. 

OTP_RESEND_COOLDOWN_SECONDS: z.coerce.number().int().positive().default(60)
BE-SEC-004 · Redacción Ampliada en Logger Pino Baja · CWE-532

Se agregaron a redact.paths en src/config/logger.ts los campos de dominio en español y cabeceras de sesión: *.passwordActual, *.passwordNueva, *.codigo y res.headers["set-cookie"].

BE-SEC-005 · Allow-List de Entidad en Storage Baja · CWE-22

writeUpload() en src/services/storage.ts valida ahora /^[a-z0-9_-]+$/i.test(options.entity) antes de construir rutas de directorio, blindando la frontera contra traversal incluso ante futuros llamados dinámicos.

Controles críticos verificados sin hallazgos (BE-SEC-006 & BE-SEC-007): 100% de consultas SQL parametrizadas ($1..$N) en los 20 módulos y ejecución sin shell (execFile/spawn con arrays de argumentos) en backupFiles.ts.

Checklist de Endurecimiento en Producción (Vercel + Supabase)

front/production + back/production

Frontend en Vercel (front/production) Vercel

  • Root Directory: ./ (raíz directa de front/production) · Build: npm run build · Output: dist.
  • Cabeceras de Seguridad en vercel.json:
    • Content-Security-Policy: default-src 'self'; font-src 'self'; script-src 'self'; frame-ancestors 'none'
    • Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
    • X-Content-Type-Options: nosniff · X-Frame-Options: DENY
    • Referrer-Policy: strict-origin-when-cross-origin
    • Permissions-Policy: camera=(), microphone=(), geolocation=()
  • Proxy API: Enrutar /api/:path* al origen HTTPS del backend para mantener cookie SameSite=Strict.

Backend en Supabase (back/production) Supabase + API

  • Cifrado en Tránsito: Configurar DATABASE_URL con ?sslmode=require (o certificado CA del pooler de Supabase).
  • Secretos Criptográficos: Generar JWT_SECRET y OTP_HMAC_SECRET independientes de 256 bits (openssl rand -hex 32).
  • Emparejamiento de Origen: Fijar APP_ORIGIN exactamente al dominio HTTPS de Vercel y mantener COOKIE_SECURE=true.
  • Mínimo Privilegio BD: Operar la aplicación con un rol PostgreSQL no-superusuario con permisos únicamente sobre el esquema public.
  • Inicialización: Ejecutar database/schema.sql y database/seed.sql (sin PII real) y validar GET /api/health.
Conclusión: Ambas ramas (front/production y back/production) superan los controles de seguridad OWASP y Ley 1581 de 2012 con 0 vulnerabilidades abiertas y están listas para despliegue inmediato.
